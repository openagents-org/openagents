# Workspace availability recovery — 2026-10-09

## Evidence

- One of two API replicas averaged roughly 10 seconds per request while the
  other averaged tens of milliseconds. PostgreSQL showed dozens of connections
  idle in a transaction on the degraded replica, and application logs reported
  connection-pool timeouts and connections closed by the database's 30-second
  idle-transaction limit. The database was below its 400-connection ceiling.
- Replacing individual workers did not restore responsiveness. Redeploying the
  existing release (`beaee8df-ccef-4814-8172-3cc3d79d9057`) restored both replicas
  to averages below 130 ms in the first 1,000-request sample.
- Conversation-list queries independently failed with PostgreSQL shared-memory
  allocation errors. `/dev/shm` is only 62 MB; the data volume was not full.
  A successful `/health` response did not detect either database failure.

## Application safeguards

Database work in model probes, SSE authorization, maintenance, and synchronous
CRUD runs outside the event loop. Model probes release their authorization
transaction before waiting on the provider. Database pool/connection errors
produce a retryable, CORS-readable 503. Railway checks `/ready`, which queries
the database through the worker's actual pool; `/health` remains liveness only.
Railway's deployment readiness check is not continuous health-based routing.

## Production database containment

On October 9, parallel queries were disabled and configuration reloaded, without
a database restart:

```sql
ALTER SYSTEM SET max_parallel_workers_per_gather = 0;
SELECT pg_reload_conf();
```

The previous effective value was 2, from PostgreSQL's default. This setting is
persisted on the database volume, outside the application deployment. It trades
parallel query throughput for avoiding dynamic shared-memory exhaustion. Before
restoring parallelism, increase the container's shared-memory allocation or tune
the conversation aggregation and verify its plan under concurrent load.

Rollback, once that capacity issue is resolved:

```sql
ALTER SYSTEM RESET max_parallel_workers_per_gather;
SELECT pg_reload_conf();
```

Verify `/ready`, authenticated workspace discovery, conversation-list latency,
HTTP 5xx rates, idle transactions, and shared-memory errors after deployments.
The changes address observed failure mechanisms; the original trigger for the
replica's degradation has not been conclusively isolated.
