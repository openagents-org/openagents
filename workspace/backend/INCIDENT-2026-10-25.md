# Workspace outage, 2026-10-25 UTC

## Evidence and recovery

The public API returned immediate load-balancer 503s. Both DigitalOcean backend
nodes failed `/ready`, although the primary container's liveness check was green.
Disk usage was 14% and application CPU usage was low.

PostgreSQL remained reachable from a fresh connection. Its activity snapshot
showed 26 idle transactions (oldest 2,714 seconds), 19 tuple-lock waiters and two
transaction-ID lock waiters. Blocked statements included user `last_login_at`
updates and channel updates. Application logs repeatedly reported exhaustion of
the per-worker SQLAlchemy pool (six connections plus two overflow connections).
Pool checkout timeouts do not cancel queries already waiting on database locks.

Restarting the primary and then secondary application containers released their
transactions. Both nodes passed readiness and authenticated event smoke checks;
public discovery returned 200 in 228 ms. Access logs also showed successful real
`/v1/account/workspaces` requests. A subsequent activity snapshot found no
transaction older than 15 seconds.

The blocking transaction's original application call stack was not captured.
The exact initiating route remains unconfirmed; a restart alone is recovery,
not proof that the underlying transaction-lifetime bug is fixed.

## Containment

Application ORM transactions now set local limits:

- `DB_LOCK_TIMEOUT_MS`: 3,000 ms.
- `DB_STATEMENT_TIMEOUT_MS`: 30,000 ms.
- `DB_IDLE_TRANSACTION_TIMEOUT_MS`: 60,000 ms.

Each is a positive integer and can be overridden in the application's environment.
The settings reset at transaction end, including when using a transaction pooler.
They do not change database-wide settings, schema, or Alembic connection-level
operations. PostgreSQL timeout errors use the existing retryable, CORS-readable
503 response. A request that legitimately holds an idle transaction across a slow
external operation can now fail; such operations should release their transaction
before waiting on external services.

## Validation

The data-free PostgreSQL check in `tests/check_db_timeouts_postgres.py` verifies
statement cancellation, contention on a random advisory lock, idle-transaction
termination, recovery after rollback, and restoration of settings after commit.
It creates no tables and changes no stored data. The focused SQLite/API suite
passed 101 tests; the existing token-link self-join test also failed with the new
listener disabled (401 versus its expected 200).
