# Workspace outage, 2026-10-25 UTC

## Evidence and recovery

The public API returned immediate load-balancer 503s. Both DigitalOcean backend
nodes failed `/ready`, although the primary container's liveness check was green.
Disk usage was 14% and application CPU usage was low.

PostgreSQL remained reachable from a fresh connection. Its activity snapshot
showed 26 idle transactions (oldest 2,714 seconds), 19 tuple-lock waiters and two
transaction-ID lock waiters. Blocked statements included user `last_login_at`
updates and channel updates. Application logs repeatedly reported exhaustion of
the per-worker SQLAlchemy pool (six connections plus two overflow connections).
Pool checkout timeouts do not cancel queries already waiting on database locks.

Restarting the primary and then secondary application containers released their
transactions. Both nodes passed readiness and authenticated event smoke checks;
public discovery returned 200 in 228 ms. Access logs also showed successful real
`/v1/account/workspaces` requests. A subsequent activity snapshot found no
transaction older than 15 seconds.

The blocking transaction's original application call stack was not captured.
The exact initiating route remains unconfirmed; a restart alone is recovery,
not proof that the underlying transaction-lifetime bug is fixed.

## Containment

Application ORM transactions now set local limits:

- `DB_LOCK_TIMEOUT_MS`: 3,000 ms.
- `DB_STATEMENT_TIMEOUT_MS`: 30,000 ms.
- `DB_IDLE_TRANSACTION_TIMEOUT_MS`: 60,000 ms.

Each is a positive integer and can be overridden in the application's environment.
The settings reset at transaction end, including when using a transaction pooler.
They do not change database-wide settings, schema, or Alembic connection-level
operations. PostgreSQL timeout errors use the existing retryable, CORS-readable
503 response. A request that legitimately holds an idle transaction across a slow
external operation can now fail; such operations should release their transaction
before waiting on external services.

## Validation

The data-free PostgreSQL check in `tests/check_db_timeouts_postgres.py` verifies
statement cancellation, contention on a random advisory lock, idle-transaction
termination, recovery after rollback, and restoration of settings after commit.
It creates no tables and changes no stored data. The focused SQLite/API suite
passed 101 tests; the existing token-link self-join test also failed with the new
listener disabled (401 versus its expected 200).

## Follow-up investigation and correction

The blocked queries were indexed single-user and single-channel updates, not
large scans. Data-free EXPLAIN checks used the user primary-key and channel
indexes. No historical blocking Python stack was retained, so the first request
that triggered this incident is still unknown.

Two application defects were reproduced independently:

1. `invoke_cloud_agents` was an async BackgroundTask running synchronous ORM
   queries on the HTTP event loop. Completion routing acquires a channel row
   lock and awaits a model decision. A second cloud reply waiting synchronously
   for that lock freezes the same loop, preventing the holder from resuming and
   committing. PostgreSQL sees a lock waiter and an idle transaction; the other
   half of the cycle is in Python. A bounded concurrency regression reproduced
   the freeze and failed before the correction. A data-free PostgreSQL advisory
   lock experiment also demonstrated this event-loop lock-wait mechanism.
2. FastAPI's default request-scoped yield dependency retained the message
   request's database session until all background work finished. ORM reads
   after commit can open another transaction, retaining a pooled connection
   throughout the AI call. An actual POST /v1/events regression confirmed the
   session was still open when its cloud BackgroundTask started.

Cloud invocations now run on a bounded, dedicated worker pool, with each session
created, used and closed by its owning worker. Recursive coordinated handoffs
remain on that worker to avoid waiting for an already-full executor. Detached
workflow/integration/watch hooks use a separate executor so worker-loop shutdown
does not wait on a hook that queues another cloud invocation. Message-producing
routes close their request sessions before starting background tasks, which
already receive snapshots and own their sessions.

The three-second lock timeout remains a safeguard. Completion routing still
serializes its decision under a channel lock; a slow decision can therefore
cause a competing message to receive a retryable error. This change removes the
shared event-loop deadlock, not every source of channel contention.

Permission resolution marks last_login_at dirty, but autoflush is disabled. A
normal SELECT does not issue that UPDATE; it is emitted at an explicit flush or
commit. Thus it is incorrect to attribute a user-row write lock to every read.

Validation: 263 tests passed in the targeted cloud, message, routing, approval,
integration, sharing, service and issue suite. Four message tests failed because
their background tasks use an unconfigured localhost PostgreSQL connection; all
four also fail on the unchanged deployment commit. New regression coverage
checks event-loop responsiveness, session closure before background work,
recursive handoffs under a full cloud worker pool, and worker teardown while a
watch hook is pending. The final focused suite passed 240 tests (including the
transaction timeout tests); the four new regressions also pass independently.
